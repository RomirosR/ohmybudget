# Журнал: импорт банковской выписки (PDF) → вкладка "Операции"

Цель: пользователь загружает PDF-выписку по карте, получает превью распознанных
операций, правит их вручную и сам выбирает, что импортировать в журнал операций.
Никакой автоматики по дублям и категориям — это явная договорённость (см. ниже).

## Шаг 1 — фреймворк парсеров выписок + парсер Альфа-Банка (коммит: 7effc0e)
**Дата:** 2026-06-28
**Что сделано:**
- Пакет `backend/app/services/statement_parsers/` — реестр `PARSERS`/`BANKS`,
  расширяемый под другие банки без переделки API (новый банк = новый модуль +
  строка в реестре).
- `alfa_by.py` — парсер выписки Альфа-Банка (РБ). Использует
  `pdfplumber.extract_tables()` (не `extract_text()` — текстовый поток
  перемешивает порядок слов в ячейках, переносящихся на 2 строки, табличное
  извлечение этой проблемы не имеет).
- Пропускает строки со статусом ≠ "Завершено успешно".
- `is_income` определяется **только** по явному знаку `+`/`-` перед суммой; если
  знака нет — расход по умолчанию, пользователь правит вручную в превью. Никаких
  эвристик по ключевым словам типа операции (осознанное решение — не усложнять).
- `category` = колонка "Детализация" (прямое копирование, без догадок).
- `backend/pyproject.toml` — добавлена зависимость `pdfplumber`.
- `backend/tests/fixtures/sample_statement_alfa_by.pdf` — синтетическая выписка
  (вымышленные ФИО/счёт/транзакции, сгенерирована одноразовым скриптом через
  `reportlab`, который не закоммичен — только результат).
- `backend/tests/test_pdf_statement_parser.py` — юнит-тесты парсера.

**Почему так:** табличный парсинг pdfplumber устойчивее построчного regex-разбора
текстового потока — проверено на реальной выписке пользователя (не коммитилась в
репозиторий, содержит личные данные) и на синтетической фикстуре.

**Как проверить:** `cd backend && pytest tests/test_pdf_statement_parser.py -v`.

## Шаг 2 — эндпоинты импорта (коммит: 35a953f)
**Дата:** 2026-06-28
**Что сделано:**
- `GET /api/meta/import-banks` — список банков с доступным парсером (для
  выпадающего меню на фронте).
- `POST /api/operations/import/parse` — multipart (`file` + `bank`), валидация
  `content-type`/размера (≤10 МБ)/известности банка, возвращает
  `list[OperationCreate]` **без сохранения** (превью).
- `POST /api/operations/import/confirm` — принимает отобранные пользователем
  строки превью, создаёт операции через существующий `operation_repo.create`.
- Модель/схема `Operation` не менялись — превью использует тот же
  `OperationCreate`, что и обычная ручная форма. Никакого отслеживания дублей по
  номеру транзакции — пользователь сам решает, какие строки оставить (чекбоксы на
  фронте).
- `backend/pyproject.toml` — добавлена зависимость `python-multipart` (нужна
  FastAPI для `UploadFile`/`Form`).
- `backend/tests/test_operations_import.py` — интеграционные тесты (неизвестный
  банк, не-PDF файл, отсутствие авторизации, успешный сценарий parse→confirm).

**Почему так:** превью отделено от сохранения, чтобы пользователь мог поправить
категорию/тип и исключить ненужные строки до того, как они попадут в журнал
операций.

**Как проверить:** `cd backend && pytest tests/test_operations_import.py -v`.

## Шаг 3.1 — правки по итогам ручной проверки (коммит: 600f2b7)
**Дата:** 2026-06-28
**Что сделано:**
- Категория в превью импорта — строгий `<select>` из существующих категорий
  вместо `datalist` (свободный текст не годился для итогового импорта).
- `formatMoney` (`frontend/src/lib/format.tsx`) — `maximumFractionDigits` 0 → 2:
  копейки реальных сумм (например, импортированных из выписки) не должны
  пропадать в отображении таблицы операций. В БД суммы и раньше хранились точно
  — это была только видимость округления в UI, баг затрагивал все операции.

**Почему так:** обнаружено пользователем при ручной проверке импортированных
сумм с копейками (выписка в BYN) и при попытке выбрать категорию из списка.

**Как проверить:** вкладка "Операции" — импортировать выписку, убедиться, что
категория выбирается строго из выпадающего списка и суммы показываются с
копейками в таблице операций.

## Шаг 3.2 — кнопка импорта в отдельной модалке + валидация полей (коммит: 588be1b)
**Дата:** 2026-06-28
**Что сделано:**
- Инлайн-блок (select банка + file input прямо на странице) заменён на кнопку
  "Выгрузить из выписки" + отдельная модалка `ImportBankModal.tsx`: выбор банка,
  стилизованная кнопка "Выбрать файл" (скрытый `<input type="file">` через `ref`,
  без CSS-трюка с прозрачным оверлеем — он давал баг с перехватом кликов) и
  кнопка "Выгрузить".
- Валидация — каждое поле (банк, файл) проверяется отдельно при попытке отправки
  и подсвечивается своей ошибкой `FieldError` рядом с собой, а не общей строкой
  внизу. Кнопка "Выгрузить" больше не `disabled` по незаполненным полям — у
  `button.primary` нет стиля для `:disabled`, поэтому неактивная кнопка выглядела
  как активная и пользователь не понимал, почему клик ничего не делает.

**Почему так:** при ручной проверке кнопка "Выгрузить" казалась рабочей, но клик
не доходил до бэкенда — оказалось, что выбор банка в select просто не был сделан
(плейсхолдер "Выберите банк" выглядел как нормальный пункт), а отсутствие
визуальной реакции на `disabled` маскировало проблему. Явная валидация с текстом
ошибки у каждого поля устраняет эту неоднозначность.

**Как проверить:** вкладка "Операции" → "Выгрузить из выписки" → попытаться
нажать "Выгрузить" без выбора банка/файла — под каждым полем должна появиться
своя ошибка; после выбора обоих полей — импорт проходит как раньше.

## Шаг 3 — фронтенд: импорт PDF на вкладке "Операции" (коммит: f66f634)

- `frontend/src/pages/OperationsPage.tsx` — блок импорта (выбор банка + файл)

**Почему так:** превью переиспользует существующие компоненты формы

выбрать банк, загрузить PDF, отредактировать/отметить строки в превью, подтвердить
импорт, убедиться что в таблице операций появились только выбранные записи.

## Шаг 4 — обобщённый парсер (любой банк), Tier 2 (коммит: 975960b)
**Дата:** 2026-06-29
**Что сделано:**
- Изучили рынок готовых решений (см. обсуждение в чате/PR): open banking
  агрегаторы (Plaid/Tink/Salt Edge) не покрывают банки РБ; коммерческие OCR/AI
  сервисы (Parseur, Veryfi, DocuClipper) платные и отправляют выписки на сторону —
  не годится для приватного трекера бюджета. Из опенсорса ближе всего
  [bankstatementparser](https://github.com/sebastienrousseau/bankstatementparser)
  (гибрид деterministic+LLM/vision), но это нишевая зависимость без проверки на
  кириллице — решили не тащить, реализовать Tier 2 (обобщённый табличный парсер)
  самостоятельно. Tier 3 (LLM-фоллбэк для нетабличных/сканированных выписок)
  осознанно отложен — платно и требует отправки данных вовне, отдельное решение.
- `backend/app/services/statement_parsers/_common.py` — вынесены `extract_tables`
  (pdfplumber по всем страницам, с обёрткой ошибки в `ValueError`) и `clean`
  (нормализация пробелов) — использовались только внутри `alfa_by.py`, теперь общие.
  `alfa_by.py` отрефакторен на них без изменения поведения (тесты не менялись).
- `backend/app/services/statement_parsers/generic.py` — новый парсер: ищет
  таблицу операций по смыслу заголовков колонок (дата/время, сумма, дебет,
  кредит, описание, статус — RU+EN, поиск регистронезависимый), а не по
  фиксированным индексам колонок конкретного банка. Сумма — через дебет/кредит
  или через знак `+`/`-` перед числом в единой колонке (без знака — расход по
  умолчанию, никаких других эвристик). Статус — deny-list по словам-маркерам
  отказа/ожидания (`отказ`, `fail`, `pending`, `обработке` и т.п.), если колонка
  статуса не нашлась — фильтрации нет.
- Дата — через `python-dateutil` (`dateutil.parser.parse`) вместо ручного списка
  форматов. **Важный нюанс**: `dayfirst=True` ломает ISO-строки с годом впереди
  (`"2026-01-05"` → 5 мая вместо 5 января) — добавлена проверка на ведущий
  4-значный год, и для таких строк `dayfirst=False`.
- Зарегистрирован в `PARSERS`/`BANKS` под `"generic"` ("Другой банк (автоматически
  по таблице)") — **фронтенд не менялся**, список банков в `ImportBankModal`
  подтягивается с `/api/meta/import-banks` динамически.
- Кросс-тест: `generic.parse` прогнан на существующей фикстуре Альфа-Банка
  (`sample_statement_alfa_by.pdf`) и даёт те же дату/сумму/тип/категорию, что и
  `alfa_by.parse` (отличается только `description` — generic не комбинирует
  место+страну, у него нет такой колонки-синонима). Это подтверждает, что Tier 2
  — реальное расширение функционала, а не отдельная непересекающаяся ветка.
- Новые фикстуры: `sample_statement_generic_debit_credit.pdf` (EN, дебет/кредит,
  одна строка отфильтрована по статусу "Rejected") и
  `sample_statement_generic_signed_amount.pdf` (RU, одна колонка суммы со знаком).

**Почему так:** пользователь явно отказался от LLM/внешних сервисов на этом шаге
(приватность финансовых данных, отсутствие платных зависимостей) и подчеркнул, что
обобщённый парсер должен расширять, а не дублировать существующий — отсюда
кросс-тест на фикстуре Альфы как критерий приёмки.

**Как проверить:** `cd backend && pytest` (включая
`tests/test_generic_statement_parser.py` и обновлённый
`tests/test_operations_import.py`); вручную — вкладка "Операции" → "Выгрузить из
выписки" → в списке банков должен появиться пункт "Другой банк (автоматически по
таблице)" без каких-либо правок фронтенда.
